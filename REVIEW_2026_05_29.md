### Cumplimiento de principios POO (UT1)

#### Discriminación por tipo en lugar de polimorfismo (-0,5)

Sigue exactamente igual que en la revisión anterior. En `infrastructure/repositories/edificio_repository_sqlite.py:107-116`, el método `agregar_dispositivo` decide qué guardar inspeccionando la subclase con `isinstance`:

```python
if isinstance(dispositivo, Sensor):
    tipo = "SENSOR"
    estado = None
elif isinstance(dispositivo, Actuador):
    tipo = "ACTUADOR"
    estado = 1 if dispositivo.estado else 0
```

Además, en `listar_dispositivos` (líneas 195-201), al reconstruir un actuador desde la BD se asigna directamente al atributo público:

```python
actuador = Actuador(nombre)
actuador.estado = bool(estado) if estado is not None else False
```

**Por qué importa.** El repositorio sabe demasiado sobre las subclases del dominio. Si mañana se añade un `Termostato`, hay que tocar dos sitios del repositorio (la cadena `isinstance` al guardar y la cadena `if tipo == "..."` al cargar). En POO eso lo debe declarar la propia subclase.

**Cómo arreglarlo** (misma receta de la revisión anterior):

1. En `domain/entities/sensor.py`:
   ```python
   class Sensor(Dispositivo):
       TIPO = "SENSOR"
       def estado_para_bd(self):
           return None
   ```

2. En `domain/entities/actuador.py`. Aprovechamos para convertir `estado` en atributo protegido con lectura por `@property` y sin setter público; así nadie puede modificarlo desde fuera saltándose `activar()` / `desactivar()`:
   ```python
   class Actuador(Dispositivo):
       TIPO = "ACTUADOR"

       def __init__(self, nombre, estado=False):
           super().__init__(nombre)
           self._estado = estado

       @property
       def estado(self):
           return self._estado

       def activar(self):
           self._estado = True

       def desactivar(self):
           self._estado = False

       def estado_para_bd(self):
           return 1 if self._estado else 0
   ```

3. En el repositorio (`infrastructure/repositories/edificio_repository_sqlite.py`, método `agregar_dispositivo`, líneas 107-116):
   ```python
   tipo = dispositivo.TIPO
   estado = dispositivo.estado_para_bd()
   ```

   Y en el mismo fichero, para reconstruir desde BD (método `listar_dispositivos`, líneas 187-201), un mapa simple sustituye al `if/elif`:
   ```python
   CLASES_DISPOSITIVO = {"SENSOR": Sensor, "ACTUADOR": Actuador}
   ClaseDispositivo = CLASES_DISPOSITIVO[tipo]
   dispositivo = ClaseDispositivo(nombre)
   ```

   Con el mapeado anterior los sensores se reconstruyen bien, pero el actuador se queda con `estado = False` por defecto, perdiendo el valor real guardado en BD. Esto se resuelve gracias al parámetro `estado` opcional del constructor que añadimos en el paso 2: el repositorio pasa el estado al construir, sin tocar atributos desde fuera. `listar_dispositivos` queda así:

   ```python
   ClaseDispositivo = CLASES_DISPOSITIVO[tipo]
   if tipo == "ACTUADOR":
       dispositivo = ClaseDispositivo(nombre, estado=bool(estado))
   else:
       dispositivo = ClaseDispositivo(nombre)
   ```

   Con eso, **el repositorio nunca toca atributos del dominio desde fuera** y `estado` queda como atributo protegido (`_estado`) con lectura por `@property` y sin setter público: la única forma de cambiarlo es vía `activar()` / `desactivar()` o por el constructor al reconstruir desde BD.

### Pendiente

- **Las altas duplicadas devuelven HTTP 500 por inconsistencia entre la excepción que lanza el caso de uso y la que captura la ruta.** Verificado con `POST /habitaciones/crear` con un nombre ya existente. La ruta `crear_habitacion` en `interfaces/web/app.py` sí captura `HabitacionYaExisteError` y `NombreInvalidoError` (devolvería 409 / 400 con re-render del formulario, que es lo correcto). El problema es que el use case `AgregarHabitacionUseCase.ejecutar` en `application/use_cases/agregar_habitacion.py:14` detecta el duplicado antes de llegar al repositorio y lanza un genérico `raise ValueError("La habitación ya existe.")`. Como la ruta no captura `ValueError`, la excepción se filtra hasta el manejador 500. El mismo problema aparece en `agregar_sensor`, `agregar_actuador`, `activar_actuador`, `desactivar_actuador`, `eliminar_habitacion`, `eliminar_dispositivo` y `consultar_estado`: todos lanzan `ValueError(...)` en vez de las excepciones de dominio que ya están definidas en `infrastructure/errores.py` y `domain/exceptions.py`. *Cómo arreglarlo:* en cada caso de uso, sustituir `raise ValueError(...)` por la excepción específica correspondiente (`HabitacionYaExisteError`, `HabitacionNoEncontradaError`, `DispositivoYaExisteError`, `DispositivoDuplicadoError`...). De esa forma las rutas, que ya están preparadas para capturarlas, harán el re-render con el código HTTP correcto. Las propias excepciones de dominio existen para eso; tirar de `ValueError` genérico anula su utilidad.

### Verificación funcional

Se ejecutó el flujo end-to-end siguiendo el README: `python crear_db.py` + `python -m interfaces.web.app`. Las páginas de lectura (`/`, `/habitaciones`, `/dispositivos/<habitacion>`, `/ayuda`) responden correctamente. Los endpoints `/api/habitaciones` y `/api/habitaciones/<nombre>` devuelven JSON con la estructura documentada (y 404 con `{"error": ...}` para nombres inexistentes). El manejador 404 HTML responde con `error.html`. Las altas vía POST de habitación, sensor y actuador funcionan, generan flashes y persisten al reiniciar la aplicación; activar y desactivar actuadores cambia el estado en BD. Eliminar una habitación con dispositivos asociados los elimina en cascada (la FK con `ON DELETE CASCADE` funciona). El único flujo con problema es el alta duplicada descrito arriba.
